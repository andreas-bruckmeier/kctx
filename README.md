# kctx

A fast, native Kubernetes context switcher and read-only cluster inspector for Linux.

`kctx` discovers every kubeconfig you have, shows their contexts in a searchable terminal list,
and hands the one you pick back to your shell so it can point `KUBECONFIG` at it. When you want
to know what a context actually *is*, it asks the cluster — read-only — and shows the version,
the nodes, the namespace and any obvious problems.

**kctx never modifies Kubernetes resources.** It issues only `GET` and `LIST` requests. It also
never writes to your kubeconfig files.

## Features

- **Instant context list.** Discovery and parsing are entirely local; no cluster is contacted
  while the list is built.
- **Searchable TUI** with fuzzy matching over context name, cluster, namespace and source file.
- **Shell integration without `eval`.** `kctx select` prints one line on stdout: a `KUBECONFIG`
  value your shell function exports.
- **Read-only live inspection**: server version, latency, node readiness and versions, namespace
  phase, and Pod/Deployment/StatefulSet/DaemonSet/Job/CronJob summaries.
- **Transparent problem reporting** — `2 Pods not Ready (api-1, api-2)`, not a health score.
- **Graceful degradation.** Credentials that may list Pods but not Nodes get everything they are
  allowed to see, with the rest labelled `unavailable (permission denied)`.
- **Scriptable**: tab-separated `list`, and `--json` for `list`, `current` and `inspect`.
- **Multi-file aware.** A kubeconfig may hold many contexts, clusters and users; several files
  may define the same context name. kctx models all of that and never guesses silently.

## Build

Requires Rust 1.89 or newer (the crate uses edition 2024; `kube` requires 1.89).

```bash
cargo build --release      # -> target/release/kctx
cargo test                 # 137 tests, none of which need a cluster
cargo clippy --all-targets -- -D warnings
```

Then put `target/release/kctx` on your `PATH`.

## Usage

```bash
kctx                       # interactive selector (same as `kctx select`)
kctx list                  # name, cluster, namespace, source, active — tab separated
kctx list --json
kctx current               # effective context name
kctx select <context>      # non-interactive selection
kctx inspect               # inspect the current context
kctx inspect <context> --namespace kube-system --timeout 5
kctx inspect --json
```

### Keys in the selector

| Key | Action |
| --- | --- |
| `↑` `↓`, `j` `k`, `Ctrl-N` `Ctrl-P` | move |
| `PgUp` `PgDn`, `Home` `End`, `g` `G` | jump |
| `/` | start searching (any other printable character does too) |
| `Backspace` | edit the query; empties back into command mode |
| `Enter` | select the highlighted context |
| `i` | open/close the details pane (this is what triggers a cluster request) |
| `r` | re-inspect, ignoring the cache |
| `Ctrl-D` `Ctrl-U` | scroll the details pane |
| `Esc` | clear the search, or cancel when there is none |
| `q`, `Ctrl-C` | cancel |

Cancelling exits with status `130` and prints nothing, so a shell wrapper leaves your environment
untouched.

## Shell integration

A child process cannot change its parent shell's environment, so `kctx` prints the value and your
shell exports it.

The function shadows the binary, so it passes the other subcommands straight through.

**bash / zsh** — in `~/.bashrc` or `~/.zshrc`:

```bash
kctx() {
    case "${1-}" in
        list | current | inspect | help | -h | --help | -V | --version)
            command kctx "$@"
            return
            ;;
    esac

    local config
    config="$(command kctx select "$@")" || return
    export KUBECONFIG="$config"
}
```

**fish** — in `~/.config/fish/functions/kctx.fish`:

```fish
function kctx
    switch "$argv[1]"
        case list current inspect help -h --help -V --version
            command kctx $argv
            return
    end

    set -l config (command kctx select $argv)
    or return
    set -gx KUBECONFIG $config
end
```

If you prefer to keep the binary reachable under its own name, call the function something else
(`kc`, `kctxs`, …) and drop the `case` block.

### How that works

`kubectl` takes `current-context` from the *first* file in `KUBECONFIG` that sets one. So instead
of editing your kubeconfig, kctx generates a tiny overlay file that contains nothing but a
context name and puts it in front of the original:

```console
$ kctx select production-eu
/home/you/.cache/kctx/contexts/production-eu.yaml:/home/you/.kube/prod.yaml

$ cat /home/you/.cache/kctx/contexts/production-eu.yaml
# Generated by kctx. Selects an existing context by name.
# Contains no credentials and overrides nothing else.
apiVersion: v1
kind: Config
current-context: "production-eu"
```

Clusters, users and credentials keep coming from your own untouched file. **No credential is ever
copied**, and overlays are written `0600` inside a `0700` directory. There is one stable overlay
per context name, so two shells selecting different contexts never interfere. When the source
file already selects the context you picked, kctx writes nothing at all and prints just that path.

If you would rather have the raw values, `--print path` and `--print context` give you the
kubeconfig path or the bare context name instead.

## Kubeconfig discovery

Searched in this order, deduplicated by canonical path (first occurrence wins, matching
`kubectl`'s merge precedence):

1. every entry of `$KUBECONFIG`, in order;
2. `~/.kube/config`;
3. kubeconfig-like files below `~/.kube/`, two levels deep.

While scanning, kctx skips `cache/`, `http-cache/`, `oidc-login/`, dotfiles, empty files, files
over 5 MiB and obvious non-kubeconfigs by extension (`.crt`, `.key`, `.pem`, …). Whatever is left
must parse as a kubeconfig and contain at least one context or cluster.

One broken file never blocks the others: it is reported on stderr and the remaining contexts stay
usable. Missing `$KUBECONFIG` entries are reported too, since you asked for them explicitly.

Additional directories are a struct field away (`DiscoverySources::scan_dirs`) — the plumbing for
a future config file is already in place, but there is no config file yet.

## Read-only guarantee

This is a structural property, not a promise:

- Exactly one module, `src/kubernetes/read.rs`, may construct a `kube::Api`. It wraps it in a
  `ReadOnly<K>` that exposes only `get` and `list`; the handle itself is a private field, so no
  other module *can* reach `create`, `replace`, `patch`, `delete` or `delete_collection`.
- Authenticated identity is derived from the kubeconfig, not from a `SelfSubjectReview` — that
  API would require a `POST`.
- `tests/readonly_guard.rs` fails the build if any source file constructs an `Api` outside that
  module, calls anything but `get`/`list` on it, or so much as mentions `PostParams`,
  `PatchParams`, `DeleteParams`, `Patch::`, a mutating HTTP method or the subject-review APIs.

Clusters are only contacted when you ask for live information: `kctx inspect`, or pressing `i` in
the selector. Requests carry a 3 s connect and 5 s response timeout inside an 8 s overall budget
(`--timeout`), transient failures are not retried, each list is capped at 500 objects (and says
so when it truncates), and results are cached for 30 seconds so browsing the list does not hammer
an API server.

## Architecture

```text
src/
  main.rs         wiring: logging, dispatch, exit codes
  cli.rs          clap surface and the non-interactive commands
  app.rs          selection state, filter state, inspection cache  (no ratatui, no kube)
  filter.rs       pure search scoring
  paths.rs        HOME/XDG resolution, overlay file-name encoding
  overlay.rs      the current-context overlay mechanism
  kubeconfig/     discovery.rs, parser.rs, context model — entirely local, never opens a socket
  kubernetes/     read.rs (the only API gateway), client.rs, inspection.rs, health.rs
  ui/             mod.rs (terminal + event loop), contexts.rs, inspection.rs
  output/         stdout renderers: TSV, JSON, inspection text
```

Rules the layering enforces:

- **stdout is a contract.** Only `output/` and the `cli` command functions write to it. The TUI
  renders to **stderr** (`ratatui::init()` writes to stdout, so the terminal is built by hand over
  `std::io::stderr`), which is what makes `config="$(kctx select)"` safe.
- `ui/*` never imports `kube`; `kubernetes/*` never imports `ratatui`; `app.rs` imports neither
  terminal nor client code and is therefore testable on its own.
- `health.rs` is pure functions from resource objects to observations, so problem detection is
  tested from JSON fixtures.
- Inspection runs as a background task feeding the event loop over a channel, so a slow or
  unreachable API server cannot freeze the UI.

### Dependencies

| Crate | Why |
| --- | --- |
| `kube` | kubeconfig parsing/merging, TLS, exec credential plugins, typed client. Defaults give rustls + ring, so no OpenSSL. |
| `k8s-openapi` (`v1_34`) | typed Node/Pod/Deployment/StatefulSet/DaemonSet/Job/CronJob |
| `ratatui` (+ its re-exported `crossterm`) | the TUI |
| `tokio` (`rt`, `macros`, `time`, `sync`, `net`) | single-threaded runtime, timeouts, channels |
| `clap` | CLI parsing |
| `serde` / `serde_json` | JSON output, and safe quoting of the overlay's context name |
| `tracing` / `tracing-subscriber` | diagnostics routed to a file, never to the terminal |
| `thiserror` / `anyhow` | typed errors in the library layers, context at the top level |

No YAML crate of our own: `kube` parses kubeconfigs (multi-document included) and resolves
relative certificate, token and exec paths, so kctx never touches kubeconfig bytes directly.

## Security

- Tokens, passwords, client certificates, private keys and exec-plugin arguments are never
  displayed, logged or copied. The context model has nowhere to put them: it records only an
  *auth method* (`token`, `client certificate`, `exec plugin (aws)`, …).
- YAML parse errors are reduced to their first line, because the parser's excerpt can quote the
  line next to a credential.
- Credential acquisition is left entirely to `kube`; kctx never spawns a process, and exec-plugin
  failure messages are not forwarded, since they can contain plugin output.
- Logging is off unless you pass `--log-file` (or set `KCTX_LOG_FILE`); filter with `--log-level`
  or `KCTX_LOG`. Nothing is ever logged to stdout or stderr.
- No telemetry, no phoning home: the only network traffic is to the API server of the context you
  asked to inspect.

## Testing

```bash
cargo test
```

137 tests, all offline: kubeconfig discovery and merge precedence, multi-context and multi-document
parsing, duplicate context names across files, contexts without namespaces, malformed and
non-kubeconfig files, secret redaction, overlay naming/permissions/idempotency (including a proof
that overlay + source merges to the intended `current-context`), filter ranking, key handling, TUI
rendering via ratatui's `TestBackend`, health analysis from JSON resource fixtures, `kube::Error`
classification, and the read-only guard.

End-to-end inspection is tested against a loopback stand-in for the API server
(`src/kubernetes/fake_api.rs`), which is how the "Nodes forbidden but Pods readable" degradation
path is covered without a cluster.

## Current limitations

- Linux/Unix only: overlay permissions and terminal handling use Unix APIs.
- The interactive selector needs stderr to be a TTY; otherwise pass a context name.
- Inspection covers one namespace at a time and the six common workload kinds; there is no
  cluster-wide workload view, no events, and no watches.
- Lists are capped at 500 objects per kind (reported, not silently truncated).
- Discovery scans `~/.kube/` two levels deep and has no configuration file yet.
- No colour/theme configuration, and no `--no-color` switch for the plain-text output (it emits
  none).
